# Storage: S3 protocol, unsigned requests (issue 64, PR 1)

Status: draft
Unit ids (`coverage/units.json`):
- `storage:route:DELETE /storage/v1/s3/{Bucket}`
- `storage:route:DELETE /storage/v1/s3/{Bucket}/{*}`
- `storage:route:DELETE /storage/v1/s3/{Bucket}/{*}?uploadId`
- `storage:route:DELETE /storage/v1/s3/{Bucket}?lifecycle`
- `storage:route:GET /storage/v1/s3`
- `storage:route:GET /storage/v1/s3/{Bucket}`
- `storage:route:GET /storage/v1/s3/{Bucket}/{*}`
- `storage:route:GET /storage/v1/s3/{Bucket}/{*}?tagging`
- `storage:route:GET /storage/v1/s3/{Bucket}/{*}?uploadId`
- `storage:route:GET /storage/v1/s3/{Bucket}?lifecycle`
Level: 2

An S3 client (AWS SDK, `rclone`, …) talks to Storage through the S3
protocol endpoint. Each request is authorized with AWS Signature V4, either
in the `Authorization` header, in the query string (presigned URL) or in a
multipart POST policy. This slice serves the request that carries no
signature at all; every signed request is a 501.

Pins: storage `v1.80.2`, supabase `v1.26.08` (`vendor.toml`). The
self-hosted compose file does not set `S3_PROTOCOL_ENABLED`, so the
reference stack registers the S3 routes. Kong's `storage-v1` route has no
`key-auth` and strips `/storage/v1`.

## Inputs

`GET` or `DELETE` on `/storage/v1/s3`, `/storage/v1/s3/`,
`/storage/v1/s3/{Bucket}`, `/storage/v1/s3/{Bucket}/` or
`/storage/v1/s3/{Bucket}/{key…}`, with any query string. The S3 command
the query and headers would select only matters after authorization, so
every command on the same path answers the same way here.

A request is unsigned when all of these hold (`extractSignature`):

- `Authorization` is absent or does not start with `AWS4-HMAC-SHA256 `
  (a Supabase JWT or `apikey` value translated by Kong counts as absent).
- The query string has no `X-Amz-Credential` parameter.
- The request is not `multipart/form-data` (Fastify parses no body for
  `GET`; see Out of scope for `DELETE`).

## Outputs

HTTP 403. With no `Accept` header, `Accept: */*`, or `Accept` equal to
`application/xml`, `text/xml` or `text/html` (after trimming and
lowercasing), the body is XML with
`Content-Type: application/xml; charset=utf-8`:

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?><Error xmlns="http://s3.amazonaws.com/doc/2006-03-01/"><Resource>bucket/key</Resource><Code>AccessDenied</Code><Message>Missing signature</Message></Error>
```

`Resource` is `request.url` (after Kong) without its query, with the first
`/s3` removed and empty segments dropped: `/s3/b//k?x=1` gives `b/k`, and
`/s3` gives the empty element `<Resource/>` (fast-xml-builder
`suppressEmptyNode`). Text is escaped as `xml.ts` does (`&`, `<`, `>`,
`\r`). The path stays percent-encoded, as in `request.url`.

`HEAD` is not part of this slice (`exposeHeadRoute: false`; `HEAD` is its
own command). The database is not used.

## Edge cases

- The trailing-slash twins (`/s3/`, `/s3/{Bucket}/`) answer the same.
- The `Authorization` prefix check is exact and case-sensitive.

## Out of scope (501)

- Signed requests: an `AWS4-HMAC-SHA256 ` `Authorization` header or an
  `X-Amz-Credential` query parameter. The SigV4 verifier, session tokens
  and every S3 command handler are not ported yet.
- Any other `Accept` header: `@fastify/accepts` negotiation (and the JSON
  error body it may select) is not ported.
- `DELETE` with a `Content-Type` and a `Transfer-Encoding` or
  `Content-Length`: Fastify parses that body first (fastify
  `lib/handleRequest.js`), and the S3 content parsers are not ported.
- A `{Bucket}` segment that is empty or longer than 100 characters
  (find-my-way `maxParamLength`), or a path whose percent-encoding does not
  decode to UTF-8: the router's not-found and bad-URL answers are not ported.
- `HEAD`, `PUT` and `POST` (PR 2 and PR 3 of the issue), and methods with no
  upstream route.
