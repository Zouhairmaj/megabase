An S3 client (AWS SDK, `rclone`, …) talks to Storage through the S3
protocol endpoint. Each request is authorized with AWS Signature V4, either
in the `Authorization` header, in the query string (presigned URL) or in a
multipart POST policy. This slice serves the request that carries no
signature at all; every signed request is a 501.

## Inputs

- `GET` on `/storage/v1/s3` or `/storage/v1/s3/`.
- `GET`, `HEAD`, `DELETE`, `POST` or `PUT` on `/storage/v1/s3/{Bucket}`,
  `/storage/v1/s3/{Bucket}/` or `/storage/v1/s3/{Bucket}/{key…}`.

Any query string. The S3 command the query and headers would select only
matters after authorization, so every command on the same path answers the
same way here.

A request is unsigned when all of these hold (`extractSignature`):

- `Authorization` is absent or does not start with `AWS4-HMAC-SHA256 `
  (a Supabase JWT or `apikey` value translated by Kong counts as absent).
- The query string has no `X-Amz-Credential` parameter.
- Fastify parses no body: always for `GET` and `HEAD`; for `DELETE` unless
  a `Content-Type` comes with a `Transfer-Encoding` or `Content-Length`;
  for `POST` and `PUT` only when there is no `Content-Type`, no
  `Transfer-Encoding`, and `Content-Length` is absent or `0` (fastify
  `lib/handleRequest.js`).
- Or, for `PUT` on `/storage/v1/s3/{Bucket}/{key…}`: the body is left
  unread. Every `PUT /:Bucket/*` command shares one Fastify route, and
  `put-object` and `upload-part` set `disableContentTypeParser`, so the
  JSON, text and XML parsers are no-ops there and any other type falls to
  the catch-all no-op parser. Megabase takes this branch for a well-formed
  `Content-Type` (`token/token`, then `; token=token` or
  `; token="text"` parameters) whose type is not `multipart`.

A `POST` with `Content-Type: multipart/form-data; boundary=…` is a POST
policy form instead. `extractSignature` reads it with `req.file()`: the
fields before the first file part, plus the file part itself under its name
(as the string `undefined`) unless that name is `file`. Without a file part
`req.file()` resolves to `undefined` and no field is read. The form is
unsigned when one of `X-Amz-Credential`, `X-Amz-Signature`, `Policy` and
`X-Amz-Date` is missing.

## Outputs

With no `Accept` header, `Accept: */*`, or `Accept` equal to
`application/xml`, `text/xml` or `text/html` (after trimming and
lowercasing), the body is XML with
`Content-Type: application/xml; charset=utf-8`. An unsigned request gets
HTTP 403:

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?><Error xmlns="http://s3.amazonaws.com/doc/2006-03-01/"><Resource>bucket/key</Resource><Code>AccessDenied</Code><Message>Missing signature</Message></Error>
```

An unsigned POST policy form gets HTTP 400 with `<Code>InvalidSignature</Code>`
and `<Message>Invalid signature format</Message>` in the same envelope.

`Resource` is `request.url` (after Kong) without its query, with the first
`/s3` removed and empty segments dropped: `/s3/b//k?x=1` gives `b/k`, and
`/s3` gives the empty element `<Resource/>` (fast-xml-builder
`suppressEmptyNode`). Text is escaped as `xml.ts` does (`&`, `<`, `>`,
`\r`). The path stays percent-encoded, as in `request.url`.

`HEAD` gets the same status, `Content-Type` and `Content-Length` with no
body (Node's `http` drops it). The database is not used.

## Edge cases

- The trailing-slash twins (`/s3/`, `/s3/{Bucket}/`) answer the same.
- The `Authorization` prefix check is exact and case-sensitive.
- A POST policy form with every signature field but whose file part is
  named `Policy` (or another of the four) counts as signed.

## Out of scope (501)

- Signed requests: an `AWS4-HMAC-SHA256 ` `Authorization` header, an
  `X-Amz-Credential` query parameter, or a POST policy form with all four
  signature fields. The SigV4 verifier, session tokens and every S3 command
  handler are not ported yet.
- Any other `Accept` header: `@fastify/accepts` negotiation (and the JSON
  error body it may select) is not ported.
- Bodies Fastify parses (see Inputs), other than the POST policy form: the
  S3 content parsers are not ported.
- POST policy forms that busboy or `@fastify/multipart` would reject or read
  differently: a malformed body or one larger than 2 MiB, a media type that
  is not exactly `multipart/form-data`, a part after the file part (busboy
  keeps adding those to `data.fields` while they are read), more than 20
  fields, a field value over 1 MiB, a repeated or non-ASCII name, or an
  `Object.prototype` name.
- `PUT` on `/s3/{Bucket}` (create bucket, `?lifecycle`) with a body: the
  XML, JSON and text parsers run there and their errors are not ported.
- `PUT` on `/s3/{Bucket}/{key…}` with a body and a missing or malformed
  `Content-Type` (Fastify's fallback for those is not ported), or a
  `multipart/*` one (`@fastify/multipart` and the POST policy reading on
  `PUT` are not ported).
- `HEAD`, `DELETE`, `POST` and `PUT` on `/s3` and `/s3/`: no route, so the
  router's not-found answer, which is not ported.
- A `{Bucket}` segment that is empty or longer than 100 characters
  (find-my-way `maxParamLength`), or a path whose percent-encoding does not
  decode to UTF-8: the router's not-found and bad-URL answers are not ported.
- Methods with no upstream route.
